# ADR-0003: استراتيجية API — واجهة v1 داخل وسيط web

## الحالة
مقبول (2026-11)

## السياق
الـ SPA يحتاج API. الخيارات: API منفصل بتوكنات Sanctum + CORS، أو نفس جلسة Blade.

## القرار
- `/api/v1` داخل `Route::prefix('api/v1')->middleware(['web', throttle])` — **مصادقة جلسة الكوكيز نفسها**، لا CORS إطلاقًا (نفس الأصل)، وCSRF مطبق على الكل ما عدا `auth/login` (أول طلب بلا جلسة؛ خنق معدل بديلًا: `LOGIN_THROTTLE_MAX`).
- **مغلّف استجابة موحد** `ApiList::paginate()`: `{ data, meta }` مع خرائط `sortable` صريحة لكل مسار (حقل الواجهة → عمود الجدول)، و`search`/`filters` per-endpoint.
- **قاعدة أمان لكل مسار {id}**: تفويض صريح (دور/سياسة أو ملكية) — سياسات IDOR موثقة في docs/audits/security-audit.md.
- انتهاء الجلسة يعيد **401 JSON** للـ SPA (وليس redirect) — معالج مخصص في bootstrap/app.php.
- خنق عام `API_THROTTLE_MAX` لكل مستخدم+IP/دقيقة.
- Blade القديم ومساراته `/api/*` الداخلية باقية كما هي — التعايش حتى اكتمال الترحيل.

## العواقب
- ✅ لا تكوين CORS، لا إدارة توكنات، وCSRF مغطى.
- ⚠️ الـ API مرتبط بجلسة الكوكيز — لا يصلح لمستهلكين خارجيين (إن لزم مستقبلًا: بادئة v2 بتوكنات Sanctum).
- ⚠️ كل حقل قابل للفرز يجب إعلانه في `sortable` خلفيًا — وإلا نقر العمود لا يفعل شيئًا (تمت تغطية كل الأعمدة الفعلية؛ الأعمدة المحسوبة معلنة `sortable: false` في الواجهة).
