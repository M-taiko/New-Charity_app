# معيار جاهزية المهمة — Definition of Ready

لا تدخل مهمة التطوير إلا إذا استوفت كل البنود التالية. المهمة غير المستوفية تُعاد للإعداد وليست "جاهزة".

## 1. الوصف والمتطلبات
- [ ] هدف واضح بجملة واحدة (ماذا يتغير ولماذا).
- [ ] المتطلبات الوظيفية مرقمة وخالية من الالتباس.
- [ ] الحالات الطرفية المحددة (بيانات فارغة، سجلات مفقودة، صلاحيات مختلفة).

## 2. معايير القبول
- [ ] قائمة قابلة للاختبار ("عند X يتوقع Y") — لا عبارات عامة.
- [ ] سيناريو للمستخدم الأقل صلاحية (ماذا يرى/ماذا يُمنع).
- [ ] سلوك الخطأ المتوقع (404/403/422/انقطاع) مع الرسالة.

## 3. عقد API (عند وجوده)
- [ ] المسار والفعل، والوسيط (auth/throttle).
- [ ] شكل الطلب (الحقول + القياس) وشكل الاستجابة (مثال JSON كامل).
- [ ] إضافة/تحديث الحقول في `sortable`/`filters` الخلفية إن أُضيف عمود جدول قابل للفرز.
- [ ] رسائل الأخطاء بالعربية بنمط `{ message, errors? }`.

## 4. الاعتماديات
- [ ] المهام/النقاط التي تسبقها، وMigrations المطلوبة.
- [ ] التراخيص/الأدوار المتأثرة (أبواب Gate).

## 5. الملفات والمكونات المعنية
- [ ] الملفات التي ستُعدَّل/تُنشأ (متحكم، خدمة، صفحة SPA، مفتاح i18n، SCSS block).
- [ ] مفاتيح الترجمة الجديدة مضافة إلى `ar.json` (وتُفحص بـ `check:i18n`).
- [ ] أي تغيير على الجداول → تحديث `columns` + `appTableCol` + `sortable` إن لزم.

## 6. غير وظيفي
- [ ] الأثر على حجم الحزمة ضمن الميزانية (`check:size`).
- [ ] إمكانية الوصول: تركيز لوحي، aria، تباين مناسب.
- [ ] لا أسرار/مفاتيح في الكود؛ `.env.example` محدث لأي متغير جديد.

## مثال معبأ (مقتطف)
> **الهدف**: إتاحة فلترة طلبات الشراء بالمورد.
> **قبول**: (1) عند اختيار مورد تعرض القائمة طلباته فقط (2) مندوب لا يرى الفلتر (3) طلب فاشل يظهر رسالة الأخطاء.
> **API**: `GET /api/v1/purchase-requests?supplier_id=` — فلتر يضاف لـ filters map.
> **ملفات**: ProcurementController، purchase-list.component، ar.json (فلتر المورد).
